# Composing Finch's generics without type gymnastics

Across TypeScript, D, and the monomorphizing trio of Rust, Zig, and Swift, one pattern recurs with enough consistency to count as a design law: languages that let generic dispatch match against **arbitrary, synthesized structural shape** (TypeScript's conditional types and `infer`, D's `is()`-probed constraints) buy huge ergonomic power at the cost of either soundness, diagnostics, or both, while languages that restrict matching to a **declared, coherence-checked, finite vocabulary** (Rust traits, Zig's tagged `std.builtin.Type`, Swift protocols) buy predictability at the cost of expressiveness they then spend years trying to claw back. TypeScript's `infer` and distributive conditional types are the most powerful mechanism studied — capable of full type-level computation — but that power produces a documented, multi-year trail of `TS2589` depth-limit errors, compiler crashes, and a named "type gymnastics" backlash ([Medium: TypeScript Complexity Has Finally Reached the Point of Total Absurdity](https://medium.com/codetodeploy/typescript-complexity-has-finally-reached-the-point-of-total-absurdity-f885232a686f)). D's template constraints look concept-like but are just boolean expressions with no declared identity, which D's own co-designer conceded makes failures *less* clear, not more ([Simple and effective approaches to constraint error messages](https://digitalmars.com/d/archives/digitalmars/D/Simple_and_effective_approaches_to_constraint_error_messages_283930.html)). Rust's attempt at TypeScript-grade specialization (RFC 1210) has been open and unshipped for a decade because it is provably unsound under lifetime erasure ([Sound and ergonomic specialization for Rust, Aaron Turon](http://aturon.github.io/tech/2018/04/05/sound-specialization/)), and Rust programmers still file open feature requests (`#52894`, eight years old) for exactly the `match-type` construct Finch already has ([Issue #52894](https://github.com/rust-lang/rust/issues/52894)). Zig gets a real type-shape switch (`@typeInfo` + `switch`) only by abandoning declared interfaces entirely, and Swift never gets multi-arm matching at all — conditional conformance is a single boolean gate. Finch's existing design — a Rust-like concept/generic system with a structural `infer`-pattern grammar reused across concept bounds, plus a `match-type` that narrows per concrete carrier at monomorphization time — already occupies a design point none of these five languages reached cleanly: sound, multi-arm, per-instantiation matching bound to declared vocabulary. The rest of this report works out which specific mechanisms from each language would extend that position and which would undermine it.

## TypeScript's `infer` is structural power without a coherence check

TypeScript's conditional-type system lets `infer` bind a type variable to whatever structurally matches at a given syntactic position inside an `extends` clause — array elements (`T extends Array<infer Item> ? Item : T`), function return types (`T extends (...args: never[]) => infer Return ? Return : never`), and even recursively nested shapes like thenables, where `Awaited<T>` peels apart `.then()` callbacks with nested `infer F` then `infer V` ([TypeScript Handbook: Conditional Types](https://www.typescriptlang.org/docs/handbook/2/conditional-types.html)). This is strictly more general than trait-based extraction: it pattern-matches against *any* structural shape the compiler can express, with no requirement that the shape be declared anywhere as an interface or trait. The same freedom underlies mapped types and template literal types, which together let a library synthesize a whole new interface's member names from an existing one — `Getters<Person>` derives `getName(): string` etc. purely by combining `keyof`, a template literal `get${Capitalize<...>}`, and the `as` remap clause introduced in TypeScript 4.1 ([TypeScript Handbook: Mapped Types](https://www.typescriptlang.org/docs/handbook/2/mapped-types.html)). It is, in effect, macro-style code generation with zero runtime cost, and the `type-challenges` repository's tens of thousands of stars are direct evidence the substrate is expressive enough to be treated as its own programming language ([type-challenges](https://github.com/type-challenges/type-challenges)).

That expressiveness has three well-documented costs Finch should treat as a checklist of failure modes to design around rather than as isolated TypeScript quirks. First, **distribution is invisible and non-optional at the definition site**: a conditional type distributes over a union automatically whenever the checked type is a "naked" type parameter, and the only way to suppress it is a `[T] extends [U]` bracket trick the definer must anticipate in advance — the caller has no way to opt in or out per call ([TypeScript Handbook: Conditional Types](https://www.typescriptlang.org/docs/handbook/2/conditional-types.html)). Practitioner material calls this "a horrible little gotcha" precisely because most people write distributive conditionals by accident ([Total TypeScript: Distributivity workshop](https://www.totaltypescript.com/workshops/type-transformations/conditional-types-and-infer/distributivity-in-conditional-types/exercise)). Second, recursive `infer` chains hit **hard, shifting compiler limits**: a tail-recursion budget and separate instantiation-depth/count counters produce `TS2589 Type instantiation is excessively deep and possibly infinite`, with real regressions between compiler versions (`microsoft/TypeScript#48552`) and even outright crashes (`#41756`) reported against working code ([microsoft/TypeScript#48552](https://github.com/microsoft/TypeScript/issues/48552), [#41756](https://github.com/microsoft/TypeScript/issues/41756)). Third, the power is layered on a **structural type system with deliberate, acknowledged unsoundness** — array covariance and bivariant method parameters are kept on purpose for JavaScript-interop ergonomics even though the TypeScript team's own FAQ and multiple open issues (`#52621`, `#1394`, `#26981`) concede they hide real type errors ([microsoft/TypeScript Wiki: FAQ](https://github.com/microsoft/TypeScript/wiki/FAQ)). None of this is a JavaScript-legacy accident Finch would inherit for free; it is the direct, unavoidable price of matching against synthesized structural shape with no declared, coherence-checked contract standing between the pattern and the type it matches.

## D's "ad hoc" reputation traces to one design split, repeated at every level

D's template system separates **specialization** (`template Foo(T : T[])`, pattern-matching on a parameter's shape) from **constraints** (`if (isIntegral!T)`, a boolean predicate) as two orthogonal compiler passes: specialization ranks candidates by a fixed type-over-value-over-alias-over-sequence hierarchy first, and constraints are applied only afterward as a pass/fail filter with no influence on that ranking — "constraints are not involved with determining which template is more specialized than another" ([D Templates spec](https://dlang.org/spec/template.html); [Template Constraints article](https://dlang.org/articles/constraints.html)). This split is D's central design choice, and the research surfaced it as the root of essentially every complaint filed against the system across two multi-year forum threads. Because a constraint is just an `&&`-chain of boolean sub-expressions with no separate declared identity, the compiler cannot report *which* conjunct failed — Norbert Nemec's core complaint was that "collecting individual requirements as an AND expression of booleans does not allow any helpful error message," and splitting a constraint into narrower overloads for better diagnostics costs you D's overload-resolution rules entirely ([Concepts vs template constraints thread](https://forum.dlang.org/thread/jabakh$te4$1@digitalmars.com)). Andrei Alexandrescu, one of the constraint feature's own co-designers, later conceded the resulting failure message is "less, not more, clear to the user what steps to take to make the code work" than no constraint at all ([Simple and effective approaches to constraint error messages](https://digitalmars.com/d/archives/digitalmars/D/Simple_and_effective_approaches_to_constraint_error_messages_283930.html)), and real users report resorting to commenting out library constraints just to get a legible compiler error ("I hate template constraints," per forum user QAston, same thread). Three competing fixes were proposed — first-failing-clause detection in conjunctive-normal form, an explicit `pragma(err)` annotation (rejected as too tedious to add everywhere), and buffered sub-error output under a verbose flag (which Walter Bright worried would become "a rather large and unstructured pile of messages") — and none of them converged into a shipped feature by the time of the fetched discussion.

The same missing-structure problem recurs at the control-flow level: D has no native compile-time pattern-matching construct at all. `static if` is compile-time-only conditional *inclusion*, composed only by chaining `else static if`, and a dedicated forum thread opens with a user's direct complaint about being "prone to leaving out the crucial 'static' after 'else'" — a syntactic footgun from reusing the runtime `if`/`else` grammar for a compile-time purpose ([static switch/pattern matching thread](https://forum.dlang.org/thread/ugiypegvtdhhvzrmfuua@forum.dlang.org)). Community members hand-rolled `match!(...)`-style template libraries as a workaround, and getting the matched value's *narrowed type* into each handler arm required passing it as an `alias` template parameter — a non-obvious trick the D community had to discover for itself rather than receiving as a language primitive. D's most celebrated ergonomic win, the eponymous template (`T max(T)(T a, T b)` instead of `template max(T) { T max(T a, T b) { ... } }`), and IFTI (implicit inference of a function template's type parameters from call-site argument types, eliminating `!(...)` almost everywhere) are genuinely good sugar with no comparable downside found in the research — but they sit on top of, and do not fix, the specialization/constraint split. The standard library's `isInputRange` idiom is real structural/duck-style matching, satisfied by member shape alone with zero declared conformance ([std.range.primitives docs](https://dlang.org/phobos/std_range_primitives.html)), and it inherits the identical diagnostic weakness: a type missing an `@property` annotation on one method fails the check silently, with no indication of which requirement was unmet.

## Monomorphizing languages all refuse to match on synthesized shape — and pay for it differently

Rust, Zig, and Swift each need the same thing TypeScript's `infer` and D's specialization provide — pull a sub-part out of a generic parameter, or branch behavior on which concrete type it was instantiated with — and each reaches it through a narrower, coherence-checked substitute rather than adopting structural pattern-matching over arbitrary shape. Rust's associated types (`type Item;` inside `Iterator`) extract a sub-type, but resolution runs through **trait matching**, not structural unification: the extracted type must be declared as part of a trait an `impl` conforms to, giving every extraction site a coherence-checked, non-overlapping table behind it ([RFC 0195](https://rust-lang.github.io/rfcs/0195-associated-items.html)). `where`/bound composition is purely conjunctive — conditional impls like `Cell<T>::get` requiring `T: Copy` compose by intersection, never by branching ([Possible Rust: Conditional Impls](https://www.possiblerust.com/pattern/conditional-impls)). Full specialization (RFC 1210), which would have let one impl override a more-general blanket impl for a specific shape, has been open and unstabilized for a decade because the original design is provably unsound: a type that is *provably* `'static` at a call site can still be generic at the impl site once lifetimes are erased for codegen, so type-checking and code generation can disagree about which impl body runs ([Tracking issue #31844](https://github.com/rust-lang/rust/issues/31844); [Sound and ergonomic specialization, Aaron Turon](http://aturon.github.io/tech/2018/04/05/sound-specialization/)). Only a closed, standard-library-only `min_specialization` subset ships, and only on nightly. Lacking a general mechanism, Rust programmers who need "branch on the concrete type behind a generic parameter" reach for a documented "cursed pattern" — comparing `TypeId::of::<T>()` at runtime and `transmute_copy`/`downcast_ref` through `dyn Any` — packaged as libraries like `try-specialize` specifically to fill the gap ([Poor man's specialization in Rust](https://blog.vorona.ca/poor-mans-specializaton-in-rust.html)). Issue `#52894`, open since 2018, asks for exactly Finch's `match-type` construct — "conditional compilation based on the type of a type parameter," to run "during/after monomorphisation" — and remains unresolved ([Issue #52894](https://github.com/rust-lang/rust/issues/52894)).

Zig and Swift sit at opposite ends of the remaining design space. Zig ships, as a stable feature, `@typeInfo(T)` returning a tagged union (`std.builtin.Type`) that a generic function can `switch` on directly — the closest thing among the three languages to a real, general, compile-time match on instantiated-type-shape ([luisllamas.es: Generics in Zig](https://www.luisllamas.es/en/zig-generic-types-comptime/)). It gets this expressiveness by discarding declared interfaces altogether: `anytype` parameters are "comptime duck typing," with no interface the caller's type must satisfy ahead of time, and constraint failures surface only where a specific operation inside the function body fails to compile for that instantiation ([ikrima.dev: Zig Metaprogramming](https://ikrima.dev/dev-notes/zig/zig-metaprogramming/)). An independent critique concludes plainly that "Zig-style generics are not well-suited for most languages" precisely because this trades static, checkable interface declarations for late, per-instantiation compile errors ([typesanitizer.com](https://typesanitizer.com/blog/zig-generics.html)). Swift goes the other direction and refuses multi-arm matching entirely: conditional conformance (SE-0143, `extension Array: Equatable where Element: Equatable`) is a single boolean gate that a type either conforms through or doesn't — there is no Swift construct that branches into N different behaviors for N different concrete carrier types the way `match-type` does ([SE-0143](https://github.com/apple/swift-evolution/blob/master/proposals/0143-conditional-conformances.md)). Tellingly, Swift's own "specialization" is a different concept altogether — a SIL optimizer pass, and now an explicit `@specialized` attribute (SE-0460) — that is defined to have **no semantic effect**, purely a performance hint that never changes which protocol witness is chosen ([SE-0460](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0460-specialized.md)). Any "if `T` is exactly `Int`, do X" logic in Swift has to fall back to a runtime `as?` downcast outside the compile-time type system's guarantees entirely.

## Finch's `match-type` already sits in the gap none of the five languages filled

Laid side by side, the five languages trace a single axis: how much of "match against shape" is delegated to a declared, finite, coherence-checked vocabulary versus an open-ended structural expression. TypeScript sits at the open end (any structural shape, recursively, at the cost of depth limits, invisible distribution, and documented unsoundness). D's specialization forms sit close to TypeScript on the specialization side but layer boolean constraints with no declared identity on top, producing the "under-formalized, not unprincipled" reputation the research consistently surfaces — the mechanisms are individually well-specified, but nothing ties them into one contract the compiler can decompose for diagnostics. Rust, Zig, and Swift all sit at the closed end, but arrived there through different trades: Rust chose coherence and paid with a decade-stalled specialization RFC and an open, eight-year-old feature request for the exact thing it's missing; Zig chose expressiveness over declared interfaces and paid with duck-typed, late-surfacing errors; Swift chose soundness and simplicity and paid by giving up multi-arm matching altogether, pushing real per-type branching out to runtime casts.

Finch's stated design — a structural `infer`-based pattern grammar reused across concept bounds, plus a `match-type` that narrows per concrete carrier at the point a generic parameter is monomorphized — describes a position none of the five reached: **matching happens against declared concept/carrier vocabulary (avoiding TypeScript's and D's diagnostic and soundness problems), but it is a real multi-arm match resolved at monomorphization time with narrowing (avoiding Rust's stalled specialization and Swift's single-boolean-gate limitation), and it does not require giving up declared interfaces the way Zig's `@typeInfo` switch does.** This is not a coincidence of the research; it is the exact shape the Rust community has been requesting unsuccessfully since 2018 (`#52894`) and the exact shape Turon's "always applicable" specialization proposal was reaching for before it stalled — binding dispatch only to information that survives to monomorphization/codegen, never to information (like erased lifetimes) that can vanish between type-checking and code generation.

## Six mechanisms to adopt, and three to leave alone

Weighed against Finch's existing monomorphizing, concept-bound, non-structurally-erased design, the mechanisms below compose cleanly and should be adopted, adapted with a specific guardrail, or refused outright — in that order of confidence.

**Adopt directly.** (1) TypeScript's `infer`-inside-a-match-arm binding pattern is worth taking on its syntax merits alone — Finch already has structural `infer` reused across concept bounds, so extending it to bind sub-parts (return types, element types, associated-type-shaped payloads) inside `match-type` arms is a natural, low-risk generalization of a mechanism Finch already trusts, and it is exactly what `ReturnType<T>`/`Parameters<T>`/`Awaited<T>` demonstrate is uniformly useful once available ([TypeScript Handbook: Conditional Types](https://www.typescriptlang.org/docs/handbook/2/conditional-types.html)). (2) D's IFTI and eponymous-template ergonomics — infer generic parameters from call-site arguments by default, and let a single-member generic declaration be called as if it were that member — are pure ergonomic wins with no soundness or diagnostic downside surfaced anywhere in the research; Finch should keep explicit instantiation available only for the cases inference cannot resolve. (3) Zig's `@typeInfo`+`switch` model validates that `match-type`'s core shape (switch on a compile-time-known type descriptor, generate different code per arm) is a sound and expressive pattern in a monomorphizing compiler — Finch should read this as confirmation to keep building `match-type` out, not as pressure to also add Zig's untyped duck-typing escape hatch.

**Adopt with a specific guardrail.** (4) Template literal types and the mapped-type `as` remap clause are worth having for name synthesis (accessor/event-name generation) precisely because they are compositional and don't require recursion to be useful, but Finch should not adopt TypeScript's *implicit, invisible* union distribution — if Finch ever lets a match construct behave differently over a union-like carrier versus a single carrier, that behavior must be an explicit, visible choice at the match site (closer to `[T] extends [U]` being the default, with distribution opt-in), because the TypeScript research is unambiguous that invisible distribution baked into the *definition* rather than the *call site* is the single most-cited real-world footgun in the whole system ([Total TypeScript: Distributivity workshop](https://www.totaltypescript.com/workshops/type-transformations/conditional-types-and-infer/distributivity-in-conditional-types/exercise)). (5) D's constraint composability (arbitrary boolean expressions over predicates) is worth keeping as an *escape hatch* for expert users, but only layered underneath — never in place of — Finch's declared concept-bound vocabulary as the primary mechanism, since the research shows unambiguously that boolean-AND composition without a declared identity is what breaks diagnostics; Finch's advantage is that it already has named, declared concepts, so any constraint-composition sugar should decompose failures per-named-requirement the way a Rust trait bound failure names the exact missing trait, not the way a D `if (...)` clause degrades to "doesn't match."

**Refuse.** (6) Do not import Rust-style overlapping-impl specialization (RFC 1210) in any form that lets an impl's applicability depend on information not guaranteed to survive to monomorphization — that is the precise, well-documented soundness hole (lifetime erasure causing type-check-time and codegen-time disagreement) that has kept it unshipped for ten years, and Finch's `match-type` already gets the practical benefit (branch on concrete instantiated type) without needing overlapping-impl coherence machinery at all. Do not adopt TypeScript's unbounded structural recursion for conditional types generally — the `TS2589` depth-limit history and outright compiler crashes are the direct, foreseeable cost of matching against synthesized rather than declared shape, and Finch's concept-bound `match-type` sidesteps this by construction as long as its match arms stay bound to a finite, declared vocabulary of carriers rather than opening to arbitrary recursive structural predicates. Do not adopt Swift's single-boolean-gate conditional conformance as a *replacement* for multi-arm matching — it is strictly weaker than what Finch already has, and its only real justification in Swift (giving conformance a single, unambiguous, most-specific answer) is a problem Finch's declared-concept model with `match-type` narrowing already solves more expressively.
