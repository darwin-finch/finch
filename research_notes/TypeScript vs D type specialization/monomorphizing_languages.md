# Monomorphizing Languages: How Rust, Zig, and Swift Handle Type-Level Pattern Matching, Associated-Type Extraction, and Specialization

## Rust: associated types as `infer`-style extraction; how `where`/bounds compose

### Takeaway
Rust's associated types (`type Item;` inside a trait) are the shipped, stable mechanism for pulling a sub-part out of a type parameter's concrete type — the same job TypeScript's `infer` does inside a conditional type, but resolved through trait matching rather than structural pattern matching. `where` clauses and bounds are plain conjunctive constraints that compose by intersection, not by branching. Full specialization (RFC 1210) has been open, unstabilized, and controversial for a decade because the original design was proven unsound; only a deliberately restricted, closed-set `min_specialization` subset ships, and only for use inside the standard library.

### Cited Findings
- Associated types associate a placeholder type with a trait so trait method signatures can reference it; `Iterator`'s `type Item` stands for the element type of whatever concrete type implements `Iterator` — this is the canonical example in Rust's own docs — [Rust Reference: Associated Items](https://doc.rust-lang.org/reference/items/associated-items.html), [Rust Book ch. 20.2, Advanced Traits](https://doc.rust-lang.org/book/ch20-02-advanced-traits.html)
- Associated types were added via RFC 195, motivated by needing a way to name "output" types that are uniquely determined by an impl (unlike ordinary generic parameters, which are inputs the caller chooses) — an "output" type parameter is uniquely determined by the impl but plays no role in impl selection — [RFC 0195](https://rust-lang.github.io/rfcs/0195-associated-items.html)
- Generic associated types (GATs) extend associated types with their own generic parameters and `where` clauses, letting the extracted "sub-type" itself be generic (e.g. a `LendingIterator::Item<'a>`) — [RFC 1598: generic_associated_types](https://github.com/rust-lang/rfcs/blob/master/text/1598-generic_associated_types.md)
- `where`/bound composition is conjunctive: `impl<T: Clone> MyStruct<T> { fn f(&self) -> T { ... } }` only exists when `T: Clone` holds; this is called a "conditional impl" — a type implements methods or a trait only if its own type parameters implement specific prerequisite traits — [Possible Rust: Conditional Impls](https://www.possiblerust.com/pattern/conditional-impls)
- Concrete standard-library case of conditional impls: `Cell<T>::get` returns a copy only when `T: Copy`; `Cell<T>::take` needs `T: Default`; `Cell<[T]>::as_slice_of_cells` exists specifically for slice-shaped `T` — each capability gated by its own bound on the same struct, not by branching syntax — [Possible Rust: Conditional Impls](https://www.possiblerust.com/pattern/conditional-impls)
- RFC 1210 ("Specialization") proposes multiple trait impls for overlapping types where one is provably "more specific," using a new `default` keyword to mark overridable items:
  ```rust
  impl<T> Example for T {
      default type Output = Box<T>;
      default fn generate(self) -> Box<T> { Box::new(self) }
  }
  impl Example for bool {
      type Output = bool;
      fn generate(self) -> bool { self }
  }
  ```
  Items without `default` cannot be overridden by a more specific impl — [RFC 1210 text](https://github.com/rust-lang/rfcs/blob/master/text/1210-impl-specialization.md), [RFC 1210 rendered](https://rust-lang.github.io/rfcs/1210-impl-specialization.html)
- The RFC 1210 tracking issue (#31844, opened 2016) is still open; specialization as originally specified is unsound — it "can cause Undefined Behavior without unsafe code" — [Tracking issue #31844](https://github.com/rust-lang/rust/issues/31844)
- The concrete unsound pattern (from Aaron Turon, former Rust core/lang team member) hinges on lifetime erasure: the type checker sees a lifetime bound that later vanishes at codegen, so type-checking and code generation can disagree about which impl applies:
  ```rust
  impl<T> Bad for T {
      default fn bad(&self) { println!("generic"); }
  }
  impl<T: 'static> Bad for T {
      fn bad(&self) { println!("specialized"); }
  }
  ```
  Calling `bad()` on a value that is *provably* `'static` at the call site but generic at the impl site can pick the wrong body, because "dispatch cannot depend on lifetime information" once lifetimes are erased for codegen — [Sound and ergonomic specialization for Rust, Aaron Turon](http://aturon.github.io/tech/2018/04/05/sound-specialization/), corroborated by [Issue #45982: restrictions around lifetime dispatch](https://github.com/rust-lang/rust/issues/45982)
- Turon's proposed fix was an "always applicable" rule: only impls that remain valid under *every* possible instantiation of their generic/lifetime parameters may specialize — no `'static` constraints, no repeated type parameters, and bounds drawn only from specially-marked ("specializing") traits; he floated explicit syntax like `where specialize(T: SomeTrait)` to make the restriction visible in source rather than a hidden global rule — [Sound and ergonomic specialization for Rust](http://aturon.github.io/tech/2018/04/05/sound-specialization/)
- RFC 1210 itself separately flags that associated types on a `default`-marked blanket impl "must be treated opaquely" during type-checking to prevent code from assuming a specific associated-type identity that a later, more specific impl could change — a second, independent soundness hazard beyond the lifetime one — [RFC 1210](https://rust-lang.github.io/rfcs/1210-impl-specialization.html)
- Because full specialization stalled, Rust shipped `min_specialization`: a "minimal, sound subset of specialization intended to be used by the standard library" while the general soundness issues remain unresolved. It is **nightly-only**, gated behind `#![feature(min_specialization)]`, with no stabilization date — [min_specialization, Rust Unstable Book](https://doc.rust-lang.org/beta/unstable-book/language-features/min-specialization.html)
- A 2019 PR implemented "a feature for a sound specialization subset" as the concrete `min_specialization` mechanism, restricting specialization to cases the compiler can prove safe rather than trusting programmer-supplied `default` markers globally — [PR #68970](https://github.com/rust-lang/rust/pull/68970)

### Inferences
- The Rust community's answer to "how do I extract `T` from `Foo<T>`" is almost always: define an associated type on the trait `Foo` implements, and let trait resolution — not structural inference over an arbitrary type expression — do the extraction. This is strictly narrower than TypeScript's `infer`, which can pattern-match against *any* structural shape (tuples, function signatures, unions) without a trait/impl in between. Rust trades that generality for the guarantee that every extraction site is backed by a coherence-checked, non-overlapping impl table.
- The decade-long stall on RFC 1210 is best read as: type-checking-time dispatch and codegen-time dispatch see different information (lifetimes erased, types monomorphized), and any specialization rule must be provably stable across that gap. `min_specialization`'s restriction to a closed, standard-library-only subset is Rust choosing "shippable and sound" over "general and unsound" — precisely the tradeoff a `match-type` construct with narrowing must resolve explicitly for Finch by binding at monomorphization time only (per RFC 1210 lifetime discussion, dispatch must not depend on erased information).

### Gaps
- I found no single primary source stating the current (2026) precise rule-set of what `min_specialization` accepts/rejects beyond "minimal, sound subset for stdlib use" — the Unstable Book page fetched did not enumerate the specific restriction rules (e.g., exact treatment of marker traits, negative reasoning). A deeper read of `compiler/rustc_hir_analysis` source or the tracking issue's linked design docs would be needed for an exhaustive rule list.
- No confirmation was found of any 2024-2026 RFC revival or renewed lang-team push to stabilize any broader form of specialization; treat specialization as still "open tracking issue, no stabilization path" as of this research.

## Rust: "partial specialization over a family of shapes" and blanket impls as a substitute

### Takeaway
Rust has no shipped construct for "any `Vec<T>` where `T: Clone`" specializing over a *family* of already-implemented types the way full specialization would; on stable Rust, the closest legitimate tool is the blanket impl — a single generic impl bounded by other traits — combined with Rust's coherence (orphan) rules, which force you to choose between "one generic impl for the whole family" or "one concrete impl per type," never a mix, except through unstable specialization or unsafe workarounds.

### Cited Findings
- A blanket implementation is a trait impl that applies to any type meeting stated bounds, written in ordinary stable Rust: `impl<T> Foo for T where T: Bar + Baz` — [Rust FAQ: Blanket Implementation Pattern](https://www.rustfaq.org/en/how-to-use-the-blanket-implementation-pattern/)
- You cannot have two blanket impls of the same trait whose bounds could overlap for some type — the compiler must prove no overlap exists across the whole crate graph, including hypothetical future downstream impls, so attempting to "override" a blanket impl for one concrete type (e.g. specialize `impl<T: Ord> Foo for T` with a separate `impl Foo for f64`) is rejected as a conflicting-implementation error on stable Rust — this is exactly the "family of matching shapes" case the question asks about, and it does not work today without specialization — [greyblake: Alternative Blanket Implementations for a Single Rust Trait](https://www.greyblake.com/blog/alternative-blanket-implementations-for-single-rust-trait/), [Issue #45542: cannot specialize impl of local trait when default impl is a blanket impl bounded by non-local trait](https://github.com/rust-lang/rust/issues/45542)
- The Rust team has an active internal design thread specifically about lifting this restriction: enabling blanket impls like `impl<T: Copy> Clone for T` to be added to a family *after the fact* in a backwards-compatible way, gated by specialization rules still being worked out — [internals.rust-lang.org: Supporting Blanket Impls in Specialization](https://internals.rust-lang.org/t/blog-post-supporting-blanket-impls-in-specialization/4264)
- Where specialization is unavailable, the community's stable-Rust workaround is informally called "poor man's specialization": compare `TypeId::of::<T>()` against a concrete type's `TypeId` inside a generic function, and if equal, `transmute_copy`/`downcast_ref` through `dyn Any` to treat `T` as that concrete type for a fast path, else fall back to the generic path. Because both `T` and the target type are `'static` and known at monomorphization time, the `TypeId` comparison constant-folds away, making the check zero-cost after optimization — [Poor man's specialization in Rust, Lifeboat blog](https://blog.vorona.ca/poor-mans-specializaton-in-rust.html), also documented as the `try-specialize` and `castaway` crates built around this exact pattern — [try-specialize on GitHub](https://github.com/zheland/try-specialize), [try-specialize docs.rs](https://docs.rs/try-specialize)
- This TypeId-comparison trick is explicitly called a "cursed pattern" by the community even while conceding it works, and is contrasted with `downcast-rs`, which specializes on already-erased `dyn Any` trait objects but "can't be used to specialize unconstrained [generic] types" — i.e., it solves a narrower, runtime-erased case, not the compile-time generic case — [Rust Users Forum: Cursed Pattern for specialization](https://users.rust-lang.org/t/cursed-pattern-for-specialization/139135) (as summarized in the same family of search results), [Internals: Extremely bad solutions to the Any 'static requirement](https://internals.rust-lang.org/t/extremely-bad-solutions-to-the-any-static-requirement/12494)
- A separate, still-open feature request (#52894, opened 2018) asks for exactly Finch's `match-type` shape directly in the language: "conditional compilation based on the type of a type parameter," phrased as pseudocode `when T is Debug { ... } else { ... }`, explicitly to run "during/after monomorphisation" — i.e., a request for compiler-native type-shape matching per generic instantiation, distinct from trait-based dispatch — [Issue #52894](https://github.com/rust-lang/rust/issues/52894)

### Inferences
- Rust deliberately keeps "one impl per (trait, type) pair, chosen by coherence, no overlap" as an absolute invariant on stable; the entire specialization effort is about relaxing that single invariant in a sound way, and it has not shipped generally in ten years. Anything resembling "match on which shape `T` has and pick different associated behavior" that Rust programmers do today is either (a) done through separate traits + blanket impls with non-overlapping bounds (a real family, but closed and coherence-checked, not "pattern matched"), or (b) done through the `TypeId`/`Any` runtime-shaped hack, which is exactly what Finch's own comparison point calls out ("a runtime `Any::downcast` for erased values") — Rust programmers reach for the *runtime* mechanism as a stand-in for the *compile-time* pattern match Finch's `match-type` provides natively.
- This makes Finch's `match-type` a genuine capability gap-filler relative to Rust: it is the thing issue #52894 asks for and the thing the `TypeId` hack fakes, but done soundly at compile time per monomorphization, which is precisely the "always applicable" boundary Turon's proposal tried (and Rust has still not shipped) to draw automatically.

### Gaps
- I did not find a primary RFC or accepted design specifically named "shape families" or "partial specialization over trait-bounded families" as a distinct, named Rust proposal separate from RFC 1210 itself; the blanket-impl-plus-specialization internals thread is the closest ongoing design work and is unresolved.

## Zig: `comptime` reflection (`@typeInfo`, `@TypeOf`) for shape-branching generics

### Takeaway
Zig ships (stable, not experimental) `comptime`-evaluated generic functions that use `@TypeOf` to obtain a value's type and `@typeInfo` to obtain a tagged union describing that type's shape, then branch on it with ordinary `switch`/`if` — there is no separate template-constraint mini-language; type-shape matching is just running normal Zig control flow at compile time over a data structure that describes a type. This is closer in spirit to D's `static if` combined with `is()` than to Rust traits, but Zig has no named-constraint/concept system at all — constraints are enforced by what compiles, not what is declared.

### Cited Findings
- `@typeInfo(T)` is a builtin that "returns a tagged union describing a type," and the tagged union type is `std.builtin.Type` — meaning a generic function can pattern-match with `switch` on the type's `Type` tag (`.Struct`, `.Int`, `.Pointer`, `.Array`, etc.) rather than needing a bespoke trait/concept syntax — [luisllamas.es: Generics in Zig — types as values and comptime](https://www.luisllamas.es/en/zig-generic-types-comptime/), [Hive: Learn Zig Series #32 — Compile-Time Reflection with @typeInfo](https://hive.blog/hive-196387/@scipio/learn-zig-series-32-compile-time-reflection-with-typeinfo)
- `@TypeOf` returns the type of an expression; documented example from the official reference: `@TypeOf(x_ptr)` yields `*const i32` for a `const` variable's address, and `try expectEqual(?[]const u8, @TypeOf(optional_value))` is used to assert an inferred type in a test — [Zig Language Reference (master)](https://ziglang.org/documentation/master/#typeInfo)
- Zig generic functions are literally functions that take a `type` as a `comptime` parameter and use it in their signature/body — the "generic" mechanism is just ordinary parameter passing where the parameter happens to be a first-class `type` value, evaluated at compile time — [luisllamas.es](https://www.luisllamas.es/en/zig-generic-types-comptime/), [LearningZig: Generics and Anytype](https://learningzig.org/lessons/19-generics-and-anytype)
- `anytype` parameters are described as "comptime duck typing": the function receives whatever concrete type is passed, and internally calls `@TypeOf`/`@typeInfo` to inspect and switch on the actual type category (e.g. `.Struct` vs `.Array`) — there is no declared interface the caller's type must satisfy ahead of time; failure surfaces as a compile error only where the mismatched operation is actually used inside the function body — [ikrima.dev: Zig Metaprogramming](https://ikrima.dev/dev-notes/zig/zig-metaprogramming/)
- The standard library ships `std.meta.trait` (imported as `pub const trait = @import("meta/trait.zig")`) with helper predicates like `isNumber()`; colloquially, "any function with the signature `fn(type) bool` could be known as a trait" in Zig — i.e., "traits" are just ordinary comptime boolean-returning functions over `type`, not a language-level construct — [ratfactor.com: meta.zig browseable source](http://ratfactor.com/zig/stdlib-browseable/meta.zig.html), [zig/lib/std/meta.zig](https://github.com/ziglang/zig/blob/master/lib/std/meta.zig)
- Other reflection builtins used for shape inspection alongside `@typeInfo` include `@hasField` and `@hasDecl` for structural presence checks, and `@field` for dynamic field access by name — enabling duck-typed structural dispatch entirely through builtins rather than a trait/concept declaration — [ikrima.dev: Zig Metaprogramming](https://ikrima.dev/dev-notes/zig/zig-metaprogramming/)
- `comptime`-qualified variables/parameters cause "the variable's value to be comptime-known, and all loads and stores of the variable to happen during semantic analysis" — the formal hook that lets `@typeInfo`/`switch` branching actually specialize the generated code per instantiation rather than deferring to runtime — [Zig Language Reference (master)](https://ziglang.org/documentation/master/#typeInfo)
- Comparing Zig to D directly: D marks compile-time-executed control flow explicitly with the `static` prefix (`static if`, `static foreach`, `static assert`), making the compile-time/run-time boundary visible at every call site; Zig instead annotates *parameters* with `comptime` — so whether a given argument in a call is required to be compile-time-known is a fact about the callee's signature, not visible from the call site itself, and D additionally splits a template's parameter list into two lists (compile-time params, then runtime params) rather than annotating individual parameters inline — [Renato Athaydes: Zig comptime — does anything come close?](https://renato.athaydes.com/posts/comptime-programming)
- A named critique of Zig's approach exists specifically on the "does it scale as a generics mechanism" question — "Zig-style generics are not well-suited for most languages" — arguing Zig's duck-typed comptime approach trades static, checkable interface declarations (what Rust concepts/traits or Finch's concept bounds give you) for late, per-instantiation compile errors — [typesanitizer.com: Zig-style generics are not well-suited for most languages](https://typesanitizer.com/blog/zig-generics.html)

### Inferences
- Zig's model is the opposite pole from Finch's stated design: Zig has no separate concept/bound declaration syntax at all — `@typeInfo` plus ordinary `switch`/`if` *is* Zig's entire type-level pattern-matching facility, and constraint violations are reported only where a specific operation fails to compile inside a specific instantiation (duck typing pushed to compile time, not runtime). Finch's `match-type` construct, which narrows a bound/concept type per matched arm, is structurally similar to what a Zig `switch (@typeInfo(T))` block accomplishes, but Finch keeps the concept-bound/structural-`infer` grammar Zig lacks — so Finch's `match-type` can be read as "Zig's comptime type-shape switch, but with Rust-style declared concepts as the arm-narrowing target type instead of falling through to untyped duck-typed field access."
- The D comparison is genuinely apt for Zig only at the "compile-time branch on type shape" level; D's `static if` is typically paired with declared template constraints (`if (isInputRange!R)`), giving D a closer resemblance to Rust/Finch's declared-bound model than Zig's builtin-only, no-declared-interface approach.

### Gaps
- I could not fetch the full official Zig Language Reference page body (only partial content came back for `@typeInfo`'s exact formal definition and the complete `std.builtin.Type` tagged-union field list); an exhaustive list of `Type` union tags (`Struct`, `Union`, `Enum`, `Pointer`, `Optional`, `ErrorUnion`, etc.) was not directly confirmed from the primary source in this pass, only inferred from secondary blog sources.
- No direct primary-source Zig core-team statement comparing itself to D was found — the D-comparison finding above rests on secondary blog/article synthesis (Renato Athaydes), not an official Zig design document.

## Swift: associated types, conditional conformance, and generic constraints; is there anything like specialization?

### Takeaway
Swift's shipped, stable answer to "constrain a generic type's capabilities based on what its type argument can do" is conditional conformance (`extension Array: Equatable where Element: Equatable`, SE-0143, implemented in Swift 4.1/4.2) layered on associated types and `where` clauses; Swift's "specialization" is a distinct, compiler-internal concept — an optimizer pass (and, as of a 2025-era proposal, an explicit `@specialized` attribute) that generates type-specific machine code for performance only, with an explicit design guarantee that it never changes which protocol witness/overload is chosen, unlike Rust's specialization which is user-visible dispatch selection.

### Cited Findings
- SE-0143 (Doug Gregor) introduces conditional conformances: "a generic type will conform to a particular protocol only when its type arguments meet certain requirements" — canonical example: `extension Array: Equatable where Element: Equatable { ... }` — implemented in Swift 4.2 (behind a flag in 4.1) — [SE-0143 proposal text](https://github.com/apple/swift-evolution/blob/master/proposals/0143-conditional-conformances.md), [Swift.org: Conditional Conformance in the Standard Library](https://www.swift.org/blog/conditional-conformance/), [HackingWithSwift: Conditional conformances — available from Swift 4.1](https://www.hackingwithswift.com/swift/4.1/conditional-conformance)
- The motivating gap SE-0143 closes: without conditional conformance, `[Int] == [Int]` compiles (there's a hand-written `==` for arrays of `Equatable` element), but `[[Int]] == [[Int]]` does *not*, because the outer arrays themselves were never declared `Equatable` — the `==` operator existing is not the same as the type conforming to the protocol, so composition (arrays of arrays, optionals of arrays, etc.) silently failed before SE-0143 — [SE-0143 proposal text](https://github.com/apple/swift-evolution/blob/master/proposals/0143-conditional-conformances.md)
- Concrete stdlib code from the implementing PRs: conditional `Equatable`/`Hashable` conformances were added for `Optional`, `Array`, and `Dictionary` directly using this feature — [apple/swift PR #13046: Use conditional conformances to implement Equatable for Optional, Array, and Dictionary](https://github.com/apple/swift/pull/13046), companion PR [#12910](https://github.com/swiftlang/swift/pull/12910)
- A richer, associated-type-driven example from the same Swift.org post: a lazily-split collection generic over a `Base: Collection` conforms conditionally to `BidirectionalCollection` only `where Base: BidirectionalCollection`, and separately gains a `split` capability only `where Element: Equatable` — showing associated types (`Base.Element`, `Base.SubSequence`) and conditional `where` constraints composing in the same declaration:
  ```swift
  extension LazySplitCollection: BidirectionalCollection
      where Base: BidirectionalCollection {
      func index(before i: Index) -> Index { /* ... */ }
  }
  ```
  — [Swift.org: Conditional Conformance in the Standard Library](https://www.swift.org/blog/conditional-conformance/)
- A follow-on amendment specifically extended SE-0143 to add `Hashable` conformance (not just `Equatable`) to more standard library types, indicating this was treated as an evolving, incrementally-extended mechanism rather than a one-shot feature — [Swift Forums: Amendment SE-0143 — Add Hashable conformance to std lib types](https://forums.swift.org/t/amendment-se-0143-conditional-conformance-add-hashable-conformance-to-std-lib-types/11401)
- Swift's "generic specialization" is a **SIL (Swift Intermediate Language) optimization pass**: it analyzes calls to generic functions module-wide (in Whole Module Optimization mode) or wherever marked `@_specialize`, and generates concrete non-generic versions of those functions, substituting direct calls in place of generic/witness-table calls — this is optimizer machinery, not a source-level dispatch-selection feature — [Medium (Luciano Almeida): Specialization of generic functions in Swift](https://medium.com/@lucianoalmeida1/specialization-of-generic-functions-in-swift-786b64ac3442)
- Single-file compilation limits this specialization/inlining to functions defined and called in the same file; Whole Module Optimization removes that boundary so the optimizer can specialize across the entire module — [Swift.org: Whole-Module Optimization in Swift 3](https://www.swift.org/blog/whole-module-optimizations/)
- The newest, most direct evidence of a *user-facing* specialization control in Swift is **SE-0460 (`@specialized` attribute)**, implemented in **Swift 6.3**. It solves a real gap: when a generic function is called only through a type-erased existential or from a separately-compiled binary framework, the compiler cannot see enough to auto-specialize, forcing a slow, protocol-witness-table dispatch path — up to "100x slower" per the proposal. `@specialized` lets a developer request specific instantiations explicitly:
  ```swift
  extension Sequence where Element: BinaryInteger {
    @specialized(where Self == [Int])
    @specialized(where Self == [UInt32])
    func sum() -> Double {
      reduce(0) { $0 + Double($1) }
    }
  }
  ```
  — [SE-0460: @specialized proposal](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0460-specialized.md)
- Critically, SE-0460 states this has **no semantic effect** — "the only (reasonably) observable difference is how quickly the code runs" — the specialized paths use the same protocol-dispatch semantics as the unspecialized fallback and the compiler runtime-checks the exact type before dispatching to a specialized version, falling back safely if no match. This is explicitly contrasted in the proposal against Rust-style specialization, which *can* change which overload/behavior resolves — [SE-0460](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0460-specialized.md)
- Separately, Swift's protocol extension dispatch rules are static/dynamic depending on declaration site: "protocol requirements use dynamic dispatch, while protocol members [added in extensions, not part of the protocol's requirement list] use static dispatch" — this static/dynamic split is sometimes used informally to get specialization-like behavior differences, but it is a well-known "gotcha" (calling through a protocol-typed value silently picks the protocol's default extension implementation, not a conforming type's override, if the method isn't a declared protocol requirement) rather than a designed pattern-matching feature — [Medium (Leandro Pérez): Swift Protocol Extensions Method Dispatch](https://medium.com/@leandromperez/protocol-extensions-gotcha-9ef1a42c83b6), [Vadim Bulavin: Overriding Methods in Swift Protocol Extensions](https://www.vadimbulavin.com/override-methods-in-swift-protocol-extension/)

### Inferences
- Swift deliberately separates two things Rust conflates under one contested word ("specialization"): (1) *which protocol conformance/witness applies* — governed entirely by conditional conformance and ordinary generic constraints, resolved at compile time with no ambiguity because Swift requires a single, most-specific, non-overlapping conformance (enforced by the compiler, similar in spirit to Rust's coherence rules); and (2) *how fast the chosen code runs* — governed by the SIL specialization optimizer and, now, the explicit `@specialized` hint. Swift never lets you pick different *behavior* per concrete type the way Rust's (attempted) specialization or a `match-type` arm would — conditional conformance can only ever add or withhold an entire protocol conformance as a unit, gated by a boolean constraint on the type argument, not branch into N different behaviors for N different concrete carrier types within one generic body.
- This means Swift has no analogue at all to Finch's `match-type` narrowing-per-arm construct; the nearest Swift concept (conditional conformance) is a *single* conditional gate ("does `Element` conform to `Equatable`, yes/no"), not a multi-arm match over which concrete type was substituted. Any "if `T` is exactly `Int`, do X, else do Y" logic in Swift has to be written as runtime type-checking (`if let intArray = array as? [Int]`) rather than a compile-time, monomorphization-time construct — a materially weaker mechanism than what both Rust's `TypeId` hack and Finch's `match-type` provide.

### Gaps
- I did not find primary-source detail on exactly how Swift's coherence/overlap checking for conditional conformances is implemented (i.e., whether two conditional conformances with overlapping-but-not-identical `where` clauses on the same protocol/type pair are rejected, and by what rule) — this would need a direct read of the Swift compiler's conformance-lookup implementation or a dedicated Swift Evolution proposal on conformance overlap, neither of which was fetched in this pass.
- SE-0460's acceptance/implementation in "Swift 6.3" was reported by the fetched proposal text itself; I did not cross-verify against a second independent source (e.g., a Swift release note) that Swift 6.3 has actually shipped as of the current date (2026-09-18) versus being merely proposed/accepted-in-principle. Treat "implemented in Swift 6.3" as sourced from the proposal document itself, not independently confirmed as released.

## Cross-language: a real, named "type-level pattern matching that narrows a generic parameter per arm," and avoiding TypeScript's "type gymnastics" reputation

### Takeaway
None of Rust, Zig, or Swift ships a single first-class construct that is exactly Finch's `match-type` (a compile-time match on which concrete type instantiated a generic parameter, narrowing the bound per arm); each language reaches the same practical need through a different, narrower substitute — Rust through trait-bound dispatch plus an informally-named "poor man's specialization"/`TypeId` hack, Zig through `@typeInfo`+`switch` (the closest thing to a real match-type, but untyped/duck-typed), and Swift through runtime `as?` downcasting, because Swift's conditional conformance is a single boolean gate, not a multi-arm match. All three avoid TypeScript's "type gymnastics" reputation by refusing to make the type-level language Turing-complete/structural in the way TypeScript's conditional-type recursion is — matching happens against declared, coherence-checked traits/protocols/tagged unions, not against arbitrary structural shape expressions.

### Cited Findings
- Zig's `@typeInfo(T)` returning a `std.builtin.Type` tagged union that a generic function `switch`es on is the closest of the three languages to a literal "type-level match statement per instantiation" — it is exactly "conceptually similar to D's `is()` inside `static if`" per the Finch design context, confirmed structurally: Zig branches on the *shape* of `T` (`.Struct`, `.Int`, `.Pointer`, etc.) at comptime and generates different code per arm, one arm per monomorphized call site — [luisllamas.es: Generics in Zig](https://www.luisllamas.es/en/zig-generic-types-comptime/), [Hive: Learn Zig Series #32](https://hive.blog/hive-196387/@scipio/learn-zig-series-32-compile-time-reflection-with-typeinfo)
- Rust's named, real-world equivalent of "downcast an erased/generic value and narrow behavior per concrete type" is the `TypeId`-comparison + `dyn Any::downcast_ref` pattern, packaged as libraries (`try-specialize`, `castaway`) precisely because the language itself provides no compile-time match-on-instantiated-type construct; the community explicitly frames this as filling the gap left by stalled specialization — [Poor man's specialization in Rust](https://blog.vorona.ca/poor-mans-specializaton-in-rust.html), [try-specialize](https://github.com/zheland/try-specialize)
- Rust's own open feature request for exactly Finch's construct (issue #52894, "conditional compilation based on the type of a type parameter," proposed to run "during/after monomorphisation") is unresolved after 8 years — direct evidence that mainstream monomorphizing languages recognize the need but have not converged on shipping it as a first-class, sound, general construct — [Issue #52894](https://github.com/rust-lang/rust/issues/52894)
- Swift has no arm-based match at all in this space; conditional conformance is binary (conform or don't, based on one `where` clause), and per-concrete-type branching falls back to `as?` runtime casts outside the type system's compile-time guarantees — [Swift.org: Conditional Conformance](https://www.swift.org/blog/conditional-conformance/) (structurally confirmed by the single-clause form of every conditional-conformance example found: `where Element: Equatable`, `where Base: BidirectionalCollection`, `where Wrapped: Equatable` — never a multi-arm `where T is A -> ...; T is B -> ...` form)
- On avoiding "type gymnastics": Rust's own type-level programming (compile-time equality proofs via associated consts / associated types) is explicitly gated behind *unstable* features (`associated_const_equality`, `generic_const_exprs`) precisely because expressing arbitrary boolean/type-level logic this way is unwieldy even to Rust practitioners — a blog post working through the size-equality-of-two-types problem needed three different techniques (associated consts, associated "TrueType/FalseType" types, const-panic assertions) to reach something that works reliably, and explicitly says the fully general approaches require nightly-only features — this is direct evidence that Rust's *type* system deliberately keeps structural/recursive type-level computation out of stable, in contrast to TypeScript where conditional-type recursion is a first-class, always-available stable feature — [geo-ant: Curiously Cumbersome Rust: Type-level Programming](https://geo-ant.github.io/blog/2023/rust-type-level-programming/)
- Rust's design philosophy note (from community design-principles discussion) frames the difference as trait-based composition versus meta-programming syntax: rather than a type-level ternary (`T extends U ? X : Y`), Rust expresses conditional capability through multiple trait impls with different bounds — the same conditional-impls pattern documented above — treated as more aligned with "explicit, compositional patterns" than a general type-level DSL — [Rust Design Patterns: Design Principles](https://rust-unofficial.github.io/patterns/additional_resources/design-principles.html) (as characterized in aggregate search synthesis; note this is a lower-confidence secondary characterization, not a direct RFC quote — see Gaps)

### Inferences
- The shared strategy across Rust, Zig, and Swift for avoiding TypeScript's reputation is the same at a structural level even though the concrete mechanisms differ enormously: **restrict what can be matched against to something coherence-checked and finite (declared traits/protocols/tagged-union type-shapes), never an arbitrary recursively-constructed structural type expression.** TypeScript's `infer`/conditional types can pattern-match against *synthesized* structural shapes (partial tuples, function overload arms, mapped-type outputs) with no upper bound on recursive depth or a central coherence authority; Rust (traits + associated types + coherence), Zig (a closed, enumerable `std.builtin.Type` tag set), and Swift (protocols + a single-clause conditional gate) all instead match against a bounded, already-declared vocabulary. Finch's `match-type`, per the design brief, already sits in this same family — it narrows against declared concept/carrier types, not synthesized structural shapes — so it does not import TypeScript's complexity failure mode by construction; the risk to police is scope creep toward Rust's stalled full-specialization ambitions (arbitrary overlapping impls) rather than toward TypeScript's structural-inference ambitions.
- Given that Zig's `@typeInfo`+`switch` is the only one of the three that is a real, shipped, general-purpose compile-time match on instantiated-type-shape, and that it succeeds specifically *because* it gave up static, declared interfaces (trading Rust/Finch-style concept bounds for late per-instantiation errors), the design lesson for Finch is that keeping `match-type` arms bound to Finch's already-existing concept/carrier vocabulary (rather than opening it to arbitrary structural predicates over a type) is what will let Finch have Zig's expressiveness without inheriting Zig's late-error-surfacing weakness that the `typesanitizer.com` critique specifically calls out.
